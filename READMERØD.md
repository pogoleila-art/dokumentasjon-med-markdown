# Oppgave 3 – Fotnoter

Markdown er et lettvekts-språk for tekstformatering som konverteres til HTML[^1]. Det brukes mye til dokumentasjon på plattformer som GitHub[^2].

[^1]: Utviklet av John Gruber i 2004.
[^2]: GitHub bruker en utvidet variant kalt GitHub Flavored Markdown (GFM).

---

# Oppgave 4 – GFM vs. standard Markdown

Eksempel på GFM-funksjoner:

- Strikethrough: ~~dette er feil~~
- Automatisk lenke: https://github.com
- @-nevning: @octocat
- Oppgaveliste:
  - [x] Skrevet eksempel
  - [ ] Sjekket om det funker

Standard Markdown (CommonMark) inneholder de grunnleggende reglene for formatering som overskrifter, lister og lenker. GitHub Flavored Markdown (GFM) er en utvidelse av dette som legger til ekstra funksjoner som tabeller, oppgavelister, strikethrough og automatiske lenker. GFM fungerer derfor stort sett overalt der Markdown fungerer, men har flere funksjoner som er spesifikke for GitHub sine plattformer.

# Oppgave 6 – Kildekritikk

Jeg så på READMEer fra prosjektene `freeCodeCamp`, `awesome-selfhosted` og `express` på awesome-readme. Alle tre bruker klare overskrifter og innholdsfortegnelse, som gjør det enkelt å finne fram i lange dokumenter. `express` sin README er kort og teknisk, med kodeeksempler rett under installasjonsseksjonen, noe som gjør det raskt å komme i gang. `freeCodeCamp` bruker badges og bilder, som gjør README-en mer visuell, men også litt overlesset for et lite prosjekt. `awesome-selfhosted` er i praksis bare en stor liste med lenker og mangler en tydelig "kom i gang"-seksjon, noe som gjør den mindre nyttig for nye brukere. Det jeg selv ville gjort annerledes er å alltid ha en kort beskrivelse og et konkret installasjonseksempel øverst, uansett hvor stort prosjektet er.
